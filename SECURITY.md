# Security Policy

## Overview

This document describes the trust boundaries, data flows, and security model of the **i2max Salesforce Toolkit** VS Code extension.

## Trust Boundaries

| Component | Trust level |
|-----------|-------------|
| VS Code extension host | Trusted — runs all TypeScript code |
| Local Salesforce CLI (`sf`) | Trusted — invoked via `child_process.execFile` with argument arrays; no shell is spawned |
| Salesforce org APIs | Semi-trusted — responses are parsed as JSON; never executed |
| Webview panels | Untrusted — all messages received from webviews are validated before acting on them |

## What Runs Locally

- All extension code runs **entirely on the developer's local machine** inside VS Code.
- Authentication is delegated entirely to the local **Salesforce CLI** (`sf`). The extension never asks users to paste passwords, tokens, or session IDs.
- OAuth access tokens obtained from `sf org display` are used exclusively as in-memory `Authorization` header values and are **never written to any log, file, or telemetry sink**.

## Outbound Network Calls

The extension makes outbound HTTPS calls **only** to the authenticated Salesforce org's own instance URL.

- Before every outbound call the hostname of the target URL is validated against `instanceUrl` as reported by `sf org display`. Requests to any other host are blocked.
- The `fetchApiVersions` helper additionally enforces that the hostname matches a known Salesforce domain pattern.
- No metadata, credentials, or usage data are ever sent to the extension developer or any third-party service.

## Shell Execution

All Salesforce CLI invocations use `child_process.execFile` with an **argument array** (never string interpolation into a shell command). This prevents shell injection regardless of the content of org usernames, aliases, or user-supplied values.

User-supplied input (aliases, SOQL, limit values) is validated or sanitized before being passed as CLI arguments.

## Secret Handling

- No secrets are stored. The extension does not use `globalState`, `workspaceState`, temporary files, or `SecretStorage` to persist OAuth tokens.
- Tokens are obtained on-demand from the local Salesforce CLI and used immediately in memory.
- The access link generated by "Generate Access Link" contains a session token (`sid=`) and is sent only to the VS Code Webview panel over the secure `postMessage` channel — it is never logged.

## What Is Never Collected

- OAuth access tokens or refresh tokens
- Salesforce org metadata or user data
- Credentials of any kind
- Telemetry or usage analytics

## Reporting a Vulnerability

If you discover a security issue, please open a **private** GitHub Security Advisory in the repository rather than a public issue. Include a description, reproduction steps, and potential impact.
